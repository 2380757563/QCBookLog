# 结论：写入官方服务器确实可以作为可选分支，但属于**次要备选方案**，和「自建联邦同步写入本地」是两条完全独立路线，我结合你两阶段规划把三种写入路径完整区分，同时讲清各自优缺点、适用取舍。

## 先梳理全部三种写入渠道

1. 写入自建NeoDB本地库（阶段二核心主线）
2. 写入官方neodb.social（你提出的补充可选分支）
3. 联邦自动广播同步到全网其他实例（依附于渠道1，公开条目自动扩散）

   阶段一：实现 阅读记录 → 获取 官方联邦信息\
   阶段二：实现 阅读记录 → 写入 官方联邦信息

## 一、方案：第三方软件直接调用官方API写入（新增书籍、书评、打分）

### 可行性

官方实例开放完整读写API，生成账号Bearer Token后，POST接口可以：

- 创建全新书籍条目
- 新增短评/长书评、阅读标记（想看/读过）、评分
- 修改、删除本人创建的内容

### 硬性约束（必须重点考虑）

1. **强依赖外网，断网完全失效**，没有离线缓冲能力；
2. **严格限流**：公益志愿者服务器，批量新建、高频提交极易触发429 Too Many Requests，批量同步场景极不稳定；
3. **数据归属不在自己手里**：账号、Token、所有创建内容存储在官方服务器，账号封禁/Token失效后，全部写入功能直接作废；
4. **联邦强制开启无法关闭**：你API提交的公开条目会自动广播到整个联邦网络，无法隔离数据；
5. **不适合高频批量业务场景**：官方服务条款不允许第三方程序重度、自动化批量写入，存在账号封禁风险；
6. 只能操作**当前Token所属账号**的数据，无法跨账号写入。

### 适用场景（仅适合少量低频需求）

- 个人自用、少量手动同步记录；
- 单纯想把软件收藏同步到自己的官方账号主页展示；
- 临时测试API写入逻辑，不做长期自动化同步。

## 二、主线方案：写入自建NeoDB（阶段二核心，优先推荐）

### 实现方式

第三方软件只对接自建本地API，新增书籍/书评直接POST写入自建数据库；

1. 联网开启联邦：公开条目会通过ActivityPub自动广播至全网（含官方实例），其他实例搜索可拉取你的条目；
2. 可随时关闭联邦：写入内容仅留存本地，不会向外扩散，完全自主可控；

### 优势对比直写官方

1. 无限流，批量同步无拦截，适配高频自动化同步；
2. 存量条目本地缓存，断网仍可查询、新增本地数据；
3. 数据完全自有，服务器、数据库自己掌控，无账号封禁风险；
4. 代码统一：软件只对接一套本地API，联网/离线环境复用同一套逻辑；
5. 灵活开关联邦，按需决定内容是否对外同步。

## 三、把「直写官方」融入你的两阶段整体规划

### 阶段一：单向拉取（不变）

第三方软件直连官方API，仅读取书籍元数据，可选分支：读取后**同步写入自建库**；
此时**不做任何写入官方的操作**，仅消费官方数据源。

### 阶段二：双向同步，拆分两条写入分支（你新增的可选分支纳入体系）

#### 分支A（主流程，长期使用）：软件 ↔ 自建NeoDB双向同步

1. 软件新增书籍/书评 → 写入自建本地库；
2. 自建开启联邦时，公开条目自动同步全网（包含官方实例）；
3. 软件定时轮询自建API，同步自建库变更到软件本地；
4. 不再直接调用官方API，所有外网数据源由NeoDB联邦底层自动拉取。

#### 分支B（可选附加逻辑，按需开启）：软件额外同步写入官方实例

在分支A基础上增加独立同步逻辑：

1. 软件完成自建库写入后，额外调用官方API，把同一条目、书评再提交一份到neodb.social；
2. 做双端冗余存储：自建库存完整副本、官方账号同步一份公开记录；
3. 独立开关控制：可配置开启/关闭「同步写入官方」，不影响主流程自建同步。

## 四、两条写入分支核心取舍对比

| 维度      | 直接写入官方实例API（可选分支）      | 写入自建NeoDB（主线方案）      |
| ------- | ---------------------- | -------------------- |
| 网络依赖    | 必须外网，断网无法写入            | 存量读写无需外网；仅联邦拉新条目需要外网 |
| 流量限流    | 严格限流，批量易封禁             | 无任何限流限制              |
| 数据控制权   | 存储在第三方公益服务器            | 100%本地自有，随时隔离数据      |
| 联邦可控性   | 强制广播，无法关闭              | 可一键开关联邦，自主决定是否对外扩散   |
| 自动化批量同步 | 不推荐，有封号风险              | 完全适配批量、定时自动化同步       |
| 代码耦合    | 两套API地址（官方+自建），需两套写入逻辑 | 仅一套本地API，统一逻辑        |
| 冗余备份    | 仅官方单份数据                | 本地永久缓存，自带分布式联邦备份     |

## 五、落地建议

1. **主线优先走自建写入+联邦同步**，作为阶段二标准方案，适配绝大多数使用场景；
2. **直写官方仅作为附加可选功能**，做成配置开关，用户按需开启，不作为核心同步链路；
3. 逻辑分层解耦：
   - 基础存储层：永远以自建NeoDB为唯一可靠数据源；
   - 外网同步层：分为两套独立逻辑：
     ① 拉取外网数据：自建联邦自动检索拉取；
     ② 推送外网数据：可选API写入官方实例 + 联邦自动广播。
4. 规避风险：自动化批量同步场景，禁用直写官方分支，仅使用自建联邦同步。
